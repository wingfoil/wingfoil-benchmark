## Context

W18 (configured variants, F7.5) has its code: the configuration places and the configuring profile and prompt
([task-140](task-140-w18-configuration-places-the-configuring-profile-and-stored-configurations.md)),
`bench scenario configure` ([task-141](task-141-w18-bench-scenario-configure-and-the-configuring-session.md)), the
configured arms and the configured docs controls
([task-142](task-142-w18-configured-arms-and-the-configured-docs-controls.md)). What the configured arms still lack is
the configurations themselves: [task-138](task-138-w18-s-requirements-and-acceptance-configured-variants-f7.5.md)'s
gate fixed their scope (S1, S2, S3 and S8 at 1.1; not S10, no 1.0) and left the sessions, four scenarios × three
harnesses, to a later task, with the approver's consent on an estimate. This is that task. Without it no configured
arm passes `validate`, so W18's "Ends with" (every arm, configured ones included, in a dry run) waits for it; the
dry runs are the next task's.

No version 1.1 has a stored result yet, so the configurations land before any 1.1 run, as REQ-FMT-04 as amended in
1.50 requires.

**The estimate** (for the approver's consent; nothing is spent before it). A configuring session is one agent step on
`claude-sonnet-5-5`, effort medium, capped at 5 EUR and 1800 s by `configuring/profile.yaml`. The nearest measured
cost is a run step on the same model; every Sonnet 5.5 step the stored campaigns hold, per arm (a scratchpad script
reading `results/*/*/runs/*/*/claude-sonnet-5-5/*/run.json`, `steps[].usage.costEur`):

```
baseline           steps  175 median 0.06 p90 0.08 max 0.15
baseline-docs      steps  189 median 0.08 p90 0.11 max 0.14
openspec           steps   54 median 0.17 p90 0.21 max 0.25
openspec-docs      steps   49 median 0.06 p90 0.09 max 0.12
speckit            steps   49 median 0.09 p90 0.16 max 0.21
speckit-docs       steps   49 median 0.06 p90 0.08 max 0.12
wingfoil           steps  215 median 0.11 p90 0.15 max 0.19
```

A configuring session reads more (the project and the tool's documentation) and writes less code; taking it at two to
four times a harness arm's dearest step, 0.4–1.0 EUR each, the twelve sessions come to about **5–12 EUR**. The
profile's cap bounds the worst case at 60 EUR; the ceiling proposed below stops well before it.

## Acceptance criteria

<!-- A spending task, as task-119: no new behaviour, so no red test; the checks are the command's and validate's. -->

1. **Twelve configurations**, one per scenario version and harness, written by `bench scenario configure
   <S>@1.1 --arm <harness> --allow-spending` for S1, S2, S3 and S8 and the harnesses wingfoil, speckit and openspec,
   each with its record (`outcome: written`) under `scenarios/<S>/1.1/configured/`; S8's wingfoil configuration
   starts from the one its 1.1 already holds and extends it (task-138, choice 3). **Characterization** (the command's
   checks: places, offences, leak scan, symbolic links).
2. **Within the ceiling:** the sessions' costs, as each record states them, sum to at most the approver's ceiling.
3. **The configured arms validate:** a campaign file naming the three configured arms and the three configured docs
   controls on the four versions passes `bench campaign validate` (no missing configuration, pin, digest, prompt or
   profile mismatch); the existing campaigns' validations are unchanged (characterization, 13 of 13).
4. **Read, not only written:** for each configuration, the files it wrote and its difference from the tool's
   defaults, summarised in the execution notes for the method page's later task (T12); anything that looks like a
   leak of a step prompt or the oracle, or a project file touched, is a bug, not a silent rerun.
5. A short note, `docs/calibration/configuring.md`, every figure generated by a script from the records: per session
   its outcome, cost, wall time and tokens, and the files written; the sum against the ceiling.

## Design

1. **One session first, then the rest.** S1 on wingfoil runs alone; its record, files and transcript are read before
   the other eleven start, so that a defect of the command or the prompt costs one session, not twelve.
2. **A budget guard in the launching script** (as task-119's): before each session it stops if the spending so far
   plus 2 EUR could pass the ceiling; sessions start only when the machine's load is low (the suites' load watcher).
3. **A session that writes no configuration** (refused for an offence, killed by a cap, failed) gets **one more
   attempt** with `--replace` only when its reason is the environment (a container or network failure), not the
   agent's choices; otherwise it becomes a bug, and the approver decides. Its record stays either way.
4. **The configurations are scenario content:** they change the four 1.1 hashes, which no result pins yet; they are
   committed on the task's branch with their records and reviewed like any content (dl-020's independent review reads
   them for leaks and for project files touched).
5. **Credentials:** the sessions read the token the runner passes; nothing of it reaches the records, the transcripts
   or the notes (the command's own guarantee, checked by grepping the written files for the token's prefix pattern,
   never printing it).
6. **Figures generated:** the note's table and sums come from a script reading `scenarios/*/1.1/configured/*.json`.
