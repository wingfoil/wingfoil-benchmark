## Context

First task of wave **W11 — Publish** of release v0.1 ([rel-v0-1](../release/rel-v0-1.md)), the last
wave of the release. The wave's "Ends with" is "first preliminary result public; repository public". This
task delivers **F5.5 results site, landing page**: an honest headline, one chart, one row per category, the
"preliminary" badge and the run count, and the public or hold-out marker (features 1.2, J1, J6.2). It also
lays down what the other two W11 tasks build on: `bench site build` and the site module.

What exists:

- `aggregate.json` per campaign execution (task-034 onwards): every value with its runs and `n`
  (REQ-FMT-07), per group of scenario, version, arm and model; slices apart (T14); M-Q1, M-Q2, M-K1–M-K4,
  M-D3, M-E1, M-F1, M-F2 and M-R1–M-R3; `preliminary` for a single run; the hold-out as counts.
- Each scenario's `categories: { primary, secondary }` (S1 C, S2 D, S3 F, S8 E).
- No `src/site` module and no `bench site` command yet (REQ-ARC-01 names `site`; REQ-ARC-02 puts it beside
  `runner` and `scoring`, under `cli`).

Scope:

- **`bench site build <campaign-id>/<n>`** (REQ-CLI-09) writes static HTML and CSS to `site/`, generated
  from `aggregate.json` only, with no client framework (REQ-RES-02). The execution's pages live at its
  permanent URL `/<campaign-id>/<n>/`; the site's root points at the execution built last. A run's
  detail is linked by its `bench run show` name, as the finding note does (W10 decision 3).
- **The landing page** (REQ-RES-03): "harness, not model" with the model's name; the headline and one
  chart; one row per category A–G with the delta per arm against baseline, A, B and G listed as "not
  covered in this campaign"; the `preliminary` badge and `n` on every value, the range when n ≥ 3 and
  "beyond variance" only when the ranges do not overlap (experiment design §4.6); hold-out results marked;
  losses, ties and wins with the same visual weight; expected failures shown as losses with the missing
  capability named.
- **One page per category** (REQ-RES-02): the category's scenarios, their metrics per arm, and the runs
  behind each value.
- **The headline and the category rows are generated by fixed rules** (W11 decision 3): a fixed map from
  category to metrics, following the goals of experiment design §1, and a headline sentence built
  mechanically from the rows' wins, losses and ties. There is no authored text. The exact map, the
  sentence's grammar and the chart (one inline SVG) are this task's design, and are stated in the
  requirements (REQ-RES-03 made precise) and on the method page (task-046).
- **Determinism** (REQ-NFR-05): the same `aggregate.json` gives the same bytes; no date in the pages;
  stable orders everywhere.
- **What is never published:** S2's answer key, the hold-out's content (only its counts), transcripts
  (task-047). The site reads nothing but the aggregate and the scenarios' public metadata.
- **Acceptance:** `results.feature` @F5.5 has three scenarios: "The landing page answers the question at a
  glance", "Losses, ties and gaps are as visible as wins", "Preliminary results are labelled". They get
  tests titled `@F5.5 <Scenario name>` (the traceability gate).

Out of scope:

- The method page: [task-046](task-046-method-page.md). This task leaves a link to it, and the method
  page's slot in the site.
- Publishing, and the transcripts as release assets: [task-047](task-047-manual-publish-and-transcript-assets.md).
- Comparing two campaigns, the profile filter and stable URLs across campaigns: F5.2 and F5.7, v0.2.
- Findings on the site: a finding note stays in `findings/` (task-044).

**Done** means:

- `bench site build` builds the landing page and the category pages from a scored, aggregated execution.
- The three @F5.5 scenarios are green.
- Tests, coverage and lint pass; `npm run test:bin` covers the command.

### W11 plan-phase decisions (proposed; accepted by the approver at pending → backlog)

1. **Three tasks, one per feature, in this order** (the approver's choice, 2026-09-30):
   - task-045, F5.5, `bench site build`, the landing page and the category pages;
   - [task-046](task-046-method-page.md), F5.8, the method page;
   - [task-047](task-047-manual-publish-and-transcript-assets.md), F5.6, `bench site publish` and the
     transcripts as release assets (REQ-RES-06).

   F5.5 goes first because it creates the site module and the command the other two extend. F5.8 needs
   the landing page's rules (the category map, the headline) to state them. F5.6 publishes what the
   other two build. No feature of W11 has high uncertainty, so there is no spike.
2. **The wave check is split: an offline half now, the public half at the release's publishing step**
   (the approver's choice, 2026-09-30). The "Ends with" says "public", which only the release's steps 3–6
   can make true: calibration, validation with a real run, the reference campaign, and the publish that
   makes the repository public (REQ-RES-04 refuses while it is private). No approved document is amended.
   - **Offline half, after task-047**, with the fake agent and no spending: `bench site build` on the W10
     wave-check executions (the real replay `cb46676b5881/1`, and the declared synthetic `/2` so that the
     site shows a loss and a range); the landing, category and method pages checked by hand against the
     aggregate; the same bytes on a second build; `bench site publish` deploying exactly `site/` to a local
     bare repository standing in for the remote; `bench site publish` refused while the real repository is
     private.
   - **Public half, at plan-003 step 6:** the approver makes the repository public and enables Pages; the
     reference campaign's execution is built and published; the transcripts are attached. It is recorded in
     rel-v0-1's W11 section then, and W11's "Verified" cell says which half holds.
   - There is no real-agent half in delivery (`real-agent-check` is not taken) and no spending in W11.
3. **The landing page's headline and category rows are generated by fixed rules** (the approver's choice,
   2026-09-30), never written by the maintainer. A fixed map, from category to metrics, follows the goals
   of experiment design §1:
   - C: M-Q1 and M-K1;
   - D: M-D1 and M-D3;
   - E: M-E1;
   - F: M-F1.

   The deltas are against baseline. The headline counts wins, losses and ties with the same weight, which
   answers T1 (maintainer bias). The exact map, including what stands in for a metric v0.1 does not
   measure, is task-045's design and REQ-RES-03's amendment.
4. **REQ-RES-06's transcripts go into task-047** (the approver's choice, 2026-09-30). Today no code
   compresses them, records the asset in `run.json`, or attaches it. task-047 compresses an execution's
   transcripts, records the asset, and prints the `gh release` command. The upload and the visibility change
   are the approver's actions at step 6. This closes W10's "Due before" (F5.6).
5. **Nothing outside this repository is changed by W11's code or tests.** The GitHub repository
   `wingfoil/wingfoil-benchmark` is private, has no Pages and no `gh-pages` branch (checked read-only on
   2026-09-30). Tests use a local bare repository and a stubbed visibility probe; no test calls GitHub.
   Making the repository public, enabling Pages and creating a release are the approver's. The hold-out
   repository is never named by URL in anything published.
6. **What W8–W10 learned applies here:**
   - never run `npm test` or `npm run test:bin` beside `npm run test:docker` (`test:bin` rebuilds `dist/`);
   - `tempDir` removes its directory when its test ends, so a cached fixture caches outputs, never paths;
   - never snapshot or write the WingFoil2 repository from tests;
   - after a merge that changes dependencies, main needs `npm ci` and `npm run build` before the wave
     check;
   - requirements are at 1.19, so W11's first amendment is 1.20; adr-004 is at amendment 4. The scoring
     image does not change in W11;
   - W10's wave-check repository (`w10-check/`, with `cb46676b5881/1` and `/2` scored and aggregated), its
     fake script and its scripts are the model for W11's check (W10 session handover, 2026-09-30);
   - each task is reviewed by a fresh, read-only agent before `in-review`, and each fix again by a second
     fresh agent; both rounds are recorded in the task's notes.

## Acceptance criteria

Classified in the design phase.

- `results.feature` @F5.5 "The landing page answers the question at a glance": "harness, not model" with
  the model's name, a headline sentence and one chart comparing the arms, one row per category with the
  delta per arm.
- `results.feature` @F5.5 "Losses, ties and gaps are as visible as wins": a loss in D and a win in F with the
  same prominence; A, B and G "not covered in this campaign".
- `results.feature` @F5.5 "Preliminary results are labelled": a single-repetition category carries
  `preliminary` and "n = 1"; hold-out results are marked.
- REQ-RES-02: static HTML and CSS, no client framework, one page per category, the execution's pages
  under `/<campaign-id>/<n>/`.
- REQ-CLI-09: an execution that is unknown or not aggregated is refused, naming it.
- REQ-NFR-05: the same aggregate gives the same site bytes; no date.
- Nothing unpublishable reaches `site/`: no answer key, no hold-out content, no transcript.
