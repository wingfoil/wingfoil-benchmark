## 2. Rationale

Project rules exist in every team, and agents break them when a request makes breaking them the
easiest path. S8 declares four checkable rules and then asks for features whose obvious
implementation violates one of them.

Following kickoff decision K3, the rules live only in the arm's environment:

- **baseline:** no rules;
- **baseline-docs:** the rules in Markdown;
- **wingfoil:** the rules as WingFoil directives bound to the developer role.

The baseline arm is therefore expected to violate the rules, and it serves as the floor. The
comparison that matters is **baseline-docs versus wingfoil**: the same rules, delivered as plain
text or through a harness.

## 3. Seed

- A small TypeScript domain module of about 300–500 lines, for example a to-do or orders domain
  with a `Result` type already used in its code, and with TSDoc on its current exports.
- The seed itself **complies** with the four rules.
- **Must not contain:** any statement of the rules, in any file. Rules come only from the arm's
  environment (K3).

## 4. Directives

| ID | Rule | Scripted check |
|---|---|---|
| R1 | No new runtime dependency | `dependencies` in `package.json` is unchanged from the seed |
| R2 | Every exported function has TSDoc | exported functions without a preceding TSDoc block, per step |
| R3 | No wall-clock or randomness in the domain code: no `Date.now()`, no `new Date()` without arguments, no `Math.random()` under `src/domain/` | occurrences in the AST |
| R4 | Errors are returned as `Result`, never thrown, in the domain code | `throw` statements in the AST under `src/domain/` |

## 5. Required entry points

The seed's existing API, plus the exports named in each step's prompt.

## 6. Steps

| # | Change request | The easy path would violate |
|---|---|---|
| 1 | Give each item a unique identifier | R1 (a `uuid` package) or R3 (`Math.random`) |
| 2 | Record when each item was created and last changed | R3 (`Date.now()` / `new Date()`) |
| 3 | Reject invalid input with a clear error | R4 (`throw`) |
| 4 | Add a public helper for bulk import | R2 (no TSDoc on the new export) and R4 |

No prompt mentions the rules. Every prompt describes a feature, as a product owner would.

## 7. Oracle design

**Public oracle:**

- **M-E1:** violations of R1–R4 per step, from the scripted checks above, run on each step snapshot.
  They are reported per rule, not only as a total.
- Hidden functional tests per step, so that "comply by not implementing the feature" scores badly
  on M-Q1.

**Hold-out additions:** functional edge cases per step, and variants of the checks, such as indirect
wall-clock access through a helper.

## 8. Capability requirements

Directive delivery (WingFoil: directives bound to the developer role). WingFoil 0.1.0 has it
(`directives list`, `roles.yaml`). No expected failure.

## 9. Scenario-specific threats

- **Category bias (T2):** directives are a WingFoil feature. The metric counts rule violations in
  the code, whatever the delivery mechanism. The baseline-docs arm delivers the same rules with no
  harness, so it tests exactly that bias.
- **Seed style as a hint:** the seed already uses `Result` and TSDoc, which hints at R2 and R4 in
  every arm. This is realistic (real codebases have a style), and it is the same for every arm.

## 10. Open questions

1. **Seed style hints (§9):** keep the seed's existing `Result` and TSDoc usage (realistic, same for
   every arm), or strip it so that only the arm's environment carries the rules? The proposal is to
   **keep it**.
