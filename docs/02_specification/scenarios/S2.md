## 2. Rationale

Defect fixing on an unfamiliar codebase is daily work. It is also where a brownfield-oriented
competitor is expected to be strong, which counters T1 and T2.

The scenario measures three things:

- whether real defects are fixed;
- whether a correct behaviour reported as a bug is **rejected** rather than "fixed";
- whether a report that repeats an already fixed defect is recognized **across a session boundary**.

## 3. Seed

- A purpose-written TypeScript module of about **1,000–1,500 lines**, written for the benchmark
  rather than taken from open source, so the model cannot recall an original. It covers:
  - products and SKUs;
  - stock levels;
  - orders with lines;
  - discounts;
  - VAT;
  - shipping;
  - order cancellation.
- A README that documents the business rules, including the rule behind the false report (for
  example, whether shipping is taxable).
- A visible test suite that passes on the seed and covers the rules only partly. The injected
  defects are not caught by it.
- **6 injected defects** of different kinds: arithmetic or rounding, boundary or off-by-one, state
  not restored on cancellation, rule interaction such as discount stacking, lookup normalization,
  and a date-boundary defect.
- **Must not contain:** comments, commit history or file names that hint at the defects. The seed
  starts as a single initial commit.

## 4. Required entry points

The seed's existing public API, unchanged in signature. Hidden tests call only that API.

## 5. Steps

Each step delivers a batch of user reports, written as users would write them: symptoms, not causes.

| # | Reports |
|---|---|
| 1 | 3 reports: 3 real defects |
| 2 | 3 reports: 2 real defects and **1 false report**, where the behaviour is correct according to the documented rules |
| 3 | 2 reports: 1 real defect and **1 duplicate**, which restates in different words a defect fixed in step 1 |

Every prompt asks the agent to handle the reports. It gives no instruction about rejecting,
deduplicating, or keeping records.

## 6. Oracle design

**Public oracle:**

- One **defect test** per reported symptom, derived from the report text. It fails on the seed and
  passes when the symptom is gone.
- The **seed suite** plus a public regression suite. Tests that pass on the seed must still pass
  (M-D3).
- **False report (M-D2):** the documented behaviour is still in place at the end of the run. A
  scripted check also confirms that the related code was not changed to "fix" it.
- **Duplicate (M-D2):** the step-1 fix is still in place. The step-3 response is scored in two
  ways:
  - by outcome: no second, conflicting change to the same behaviour;
  - by content: any git-tracked file or commit of step 3 identifies the report as already fixed.

  The content check is format-neutral (F4.8).

**Hold-out only:**

- the **answer key** (location and nature of each injected defect);
- variant tests per defect;
- an extended regression suite.

The public repository describes the defect *kinds* only, so a web lookup cannot return the fixes
(T13).

## 7. Capability requirements

None required. WingFoil 0.1.0 cannot run its bug workflow, but it can record bugs with
`memory add`. Any extra manual work shows up in the cost metrics, not as an expected failure.

## 8. Scenario-specific threats

- **Report wording leaks the cause:** reports are reviewed so that they describe symptoms only. The
  leak scan also checks them against the answer key, which lives in the hold-out.
- **The seed's quality influences the result:** the same seed is used in every arm, so this affects
  absolute values, not differences.
