## 2. Rationale

S1 is the benchmark's reference scenario:

- Its oracle is an **independent, official conformance suite**, not something the benchmark wrote.
  This protects against T1 (maintainer bias).
- It is small enough to afford repetitions, which makes it the carrier of the determinism metrics.
- Step 4 adds a related specification that shares concepts with the earlier steps. The static
  duplication metric (M-Q2) and the next-change cost (M-F2) then show whether the earlier code was
  reused or copied.

## 3. Seed

- An empty TypeScript library project:
  - `package.json` with no runtime dependencies;
  - `tsconfig.json`, strict mode;
  - a test script with no tests;
  - a README with a one-paragraph project description, the same text for every arm.
- **Must not contain:** any JSON Pointer, Patch or Merge Patch code or tests, or any copy of the
  specifications or of the conformance suite.

## 4. Required entry points

Exported from `src/index.ts`:

| Step | Export | Contract |
|---|---|---|
| 1 | `resolvePointer(document, pointer)` | returns the referenced value; throws an error when the pointer is invalid or does not resolve |
| 2 | `applyPatch(document, patch)` | returns a new document; does not mutate the input; throws on an invalid patch or a failed operation |
| 4 | `applyMergePatch(target, patch)` | returns the merged document |

Error types, internal structure and any further export are free.

## 5. Steps

| # | Intent | The prompt must say |
|---|---|---|
| 1 | Implement JSON Pointer (RFC 6901) | the RFC number, the `resolvePointer` contract, and that the result will be used by later features |
| 2 | Implement JSON Patch (RFC 6902): add, remove, replace, move, copy, test | the RFC number and the `applyPatch` contract, including "must not mutate the input" |
| 3 | Error semantics and edge cases | that users report surprising results on invalid patches and edge cases, and ask for RFC-conformant behaviour, with no list of the cases (the suite checks them) |
| 4 | Implement JSON Merge Patch (RFC 7386) | the RFC number and the `applyMergePatch` contract |

## 6. Oracle design

**Public oracle:**

- The official suite `json-patch/json-patch-tests`, pinned at commit `2a928f9`, Apache-2.0:
  - `tests.json`, 95 cases;
  - `spec_tests.json`, 17 cases.
  - Cases marked `disabled` are skipped.
  - It runs against `applyPatch` after steps 2, 3 and 4.
  - Steps 2 and 3 are scored on the same suite: step 3 is expected to raise the pass rate.
- JSON Pointer: the examples of RFC 6901 §5, scored after step 1.
- JSON Merge Patch: the examples of RFC 7386 Appendix A, scored after step 4.
- A non-mutation check: every call receives a frozen copy of its input.
- A regression check: after step 4, the Patch suite still passes as it did after step 3.

**Hold-out additions (content only in the private repository):**

- additional edge cases for Pointer escaping;
- deep-structure and large-array Patch cases;
- Merge Patch cases beyond the RFC appendix.

These reduce the value of looking the public suite up online (T13).

## 7. Capability requirements

None: the scenario needs no harness capability. WingFoil 0.2 (K5) is not expected to fail it.

## 8. Scenario-specific threats

- **Training contamination (T5):** JSON Patch is widely implemented, so the model likely knows it.
  This inflates every arm equally. It is acceptable because S1 measures *differences* between arms,
  and the hold-out additions reduce the effect.
- **Answer lookup (T13):** the public suite is on GitHub. Web requests are logged, and hold-out
  cases are scored separately, so the gap between public and hold-out pass rates is visible.
