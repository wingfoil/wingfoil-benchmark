# WingFoil Benchmark v0.1 — First preliminary result

**Date:** 2026-10-05 (draft, for the approver)
**Release element:** [rel-v0-1](../memory/release/rel-v0-1.md) · **Plan:** [plan-003](../plans/plan-003-release-v0-1.md)

v0.1 is the first public release of the WingFoil Benchmark. It runs one reference campaign on four scenarios, and
compares an AI coding agent working with WingFoil against the same agent without it. Its results are
**preliminary**: three of the four scenarios ran once per arm, and no claim of statistical significance is made.

- **Results:** <https://wingfoil.github.io/wingfoil-benchmark/c82a5e74885b/2/>
- **How the benchmark works:** the [method page](https://wingfoil.github.io/wingfoil-benchmark/c82a5e74885b/2/method.html)
  states every rule, including the ones that limit what the results can show.
- **Transcripts** of every agent session: a release asset, `transcripts.tar.gz`, of the release
  `c82a5e74885b-2`.

## What is compared

The same agent and model work through the same tasks in three arms. Only the harness around the agent changes:

- **baseline**: the agent, the starting project and a short operating manual;
- **baseline-docs**: the same, plus the information the wingfoil arm gets, as one plain Markdown file. It is a
  control for "more context, not the harness";
- **wingfoil**: the same, plus WingFoil **v0.2.2** (`12537b62`), the latest WingFoil release, with its MCP server and
  an operating manual for its process.

**Pins:** Claude Code 2.1.280, model `claude-sonnet-5`, approver policy v1. Costs are API-equivalent euros at
0.8851 EUR/USD, whatever the actual billing; the agent ran on a subscription.

## The reference campaign

Campaign `c82a5e74885b`, execution 2, 19 runs, all completed:

| Scenario | Category | Runs per arm |
|---|---|---|
| S1, implementing a third-party specification: JSON Pointer, Patch and Merge Patch (5 steps) | C Development | 3 |
| S2, a hunt for injected bugs in an order and inventory service (3 steps) | D Maintenance & Quality | 1 |
| S3, a rental module evolved over several sessions (5 steps) | F Knowledge & Continuity | 1 |
| S8, project rules under tempting change requests (4 steps) | E Governance & Compliance | 1 |
| S1 on **Opus 5**, wingfoil arm only (the comparison slice) | C | 1 |

Categories A, B and G have no scenario yet and are shown as not covered.

## Results, in short

The site's headline, generated from the comparisons:

> Against the baseline, wingfoil is better in 2, worse in 2 and the same in 2 of 6 comparisons across categories C,
> D, E and F (preliminary: n = 1 in D, E and F).

| | baseline | baseline-docs | wingfoil |
|---|---|---|---|
| **S1**, hidden tests on the final snapshot (M-Q1, n = 3) | 99.8 % | 98.0 % | 98.4 % |
| **S1**, cost per run (M-K1, n = 3) | 2.47 € | 2.22 € | 3.82 € |
| **S2**, hidden tests; the false report and the duplicate recognised | 24/24; 2 of 3 | 24/24; 2 of 3 | 24/24; 3 of 3 |
| **S3**, earlier decisions kept or revised on record (M-F1) | 3/5 | 3/5 | 4/5 |
| **S8**, rule checks kept; hidden tests | 12/16; 23/23 | 16/16; 23/23 | 16/16; 23/23 |
| Cost per run, S2 / S3 / S8 | 0.83 / 0.88 / 1.17 € | 0.96 / 1.79 / 1.35 € | 1.63 / 2.00 / 1.98 € |

How to read it:

- On **S1** every arm passes 98–100 % of the hidden tests. The differences are within the runs' spread, and the
  wingfoil arm costs about 1.5 times the baseline.
- The wingfoil arm's advantages are where it was designed to help, though each rests on a single run:
  - recall across sessions (S2: the duplicate and the false report);
  - a revision recorded rather than made silently (S3);
  - every project rule kept (S8, as baseline-docs does).
- **Cost:** the wingfoil arm costs more in every scenario, about 1.5 to 2.3 times the baseline. Most of the extra
  is the process its operating manual sets: reading rules and decisions, and recording a task and a decision record
  for each request. The method page says so, and a lighter use of WingFoil is not measured in v0.1.
- **The Opus 5 slice** completed S1 with every hidden test passed (165/165), for 23.26 €. It is reported apart from
  the main model's results.

## Execution 1, not published

The campaign first ran as execution `c82a5e74885b/1`. Three of its 19 runs failed at S1's longest step. The
runner cut the agent's output at Node's default 1 MiB buffer, so a step that wrote more than that was read as broken
and its cost was lost (bug-011). The bug was fixed in the runner (task-053), and the campaign ran again in full as
execution 2. Execution 1's records stay in the repository as the bug's evidence, and it is not published.

## Known limits

- **Preliminary:** S2, S3 and S8 ran once per arm, and only S1 has repetitions. No difference is claimed as
  significant.
- **Model:** the slice covers the wingfoil arm only, so v0.1 does not yet test whether the harness's effect depends
  on the model.
- **Tokens:** a step's token counts are the run's model's only. Claude Code also called Haiku 4.5 for its own work
  (0.27 % of the cost). The cost includes it, and the tokens do not (bug-012, for v0.2).
- **The harness under test:** WingFoil v0.2.2 has no workflow engine. Its process is followed through the operating
  manual.
- **Benchmark by WingFoil's maintainer** (threat T1): the questions and metrics were fixed before any run, and losses
  are published like wins.

## Changes in the benchmark since the specification

Built in 11 waves, then calibrated and validated. Fixes made after validation, for the campaign:

- every process output is read whole up to 256 MiB, and a bounded step is counted at its cost bound (task-053,
  bug-011);
- the models each step used are recorded with the run, from the agent's own report (task-054, requirements 1.25);
- the method page was re-read against the campaign as it ran (task-055).
