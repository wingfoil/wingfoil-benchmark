## 3. What the cycle shows

1. **The engine is driven as designed under the step-A manual, almost always.** From `dry-runs/94` and `95` on, and in
   both campaigns' S1, S2, S3 and S8, a request opens its instance (the setup opens the first, so S1's five requests
   start four), its gate ends with "Please approve" and gets "Approved. Proceed.", and the agent records the approval
   after it, then finalizes. The exceptions are in the means: on Luna, S1 and S8 start fewer instances than requests,
   and S1 asks fewer gates; on Haiku, S3 starts one more. A request's instance takes several `finalize` calls, one per
   step of its delivery.
2. **No approval was recorded with no reply in its step** in any run read, and none on another reply under the step-A
   manual as campaign-007 and campaign-008 ran it. The manual's corrections show in the dry runs: `dry-runs/88`
   stopped on statements, so its gates were answered late, in one batch, inside one instance; `dry-runs/93`, on the
   question form, recorded all its approvals on a question's reply, which task-114 recorded and corrected.
3. **S10 is the exception, as designed** (dl-029): the agent records no approval there, since the runner carries the
   scenario approver's verdicts out, and it asks more than once a request where a verdict is a rejection or the
   approver is away.
4. **Driving the cycle is commands in the agent's own context:** `workflow next` and `status` before each step's work
   and `finalize` after it, run by the agent in its session; [wingfoil-tokens.md](wingfoil-tokens.md) attributes the
   extra tokens they and the gates' resumed sessions cost.
5. **v0.2's manual never started the engine** (campaign-002's rows: no `workflow` command), as the method page states.
