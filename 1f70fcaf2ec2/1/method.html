How the benchmark works

This benchmark measures where a harness for AI coding agents makes a difference. A harness is the process and memory tooling around an agent: here, WingFoil. The same agent and model work through the same tasks with and without it, and the results are compared by fixed, published rules. This page states those rules, including the ones that limit what the results can show.

What is compared

The benchmark compares harnesses, not models. In one comparison the agent (Claude Code), its version and the model are the same in every arm. Only the harness and the files that come with it change. Runs on a second model are a separate comparison and are never mixed with same-model results.

From v0.3 some executions run another agent, OpenAI's Codex CLI, on the same scenarios and arms. They are never mixed with Claude Code's results: an execution is one agent and its models, and two agents are compared only on a page of their own, on the baseline arm. Under Codex the operating manual is AGENTS.md instead of CLAUDE.md, and an arm's MCP server is configured in Codex's own config.toml instead of a command-line flag, marked required so that a server that does not start fails the session. Codex runs on a ChatGPT Plus subscription: its costs are API-equivalent, from a pinned OpenAI price table, and are marked as such. Its wingfoil arm is the same as Claude Code's: in campaign-005 and campaign-006 the v0.2 manual on WingFoil v0.3.0, as in campaign-002, which measures WingFoil as that manual uses it, a register of documents, not WingFoil's workflow engine; in campaign-007 the step-A manual on WingFoil v0.3.1, at a revision before campaign-008's, whose agent drives the engine (below).

The agent may also call a smaller model for its own work, beside the run's model: in v0.1, Claude Code called Haiku 4.5 now and then, for a small share of the cost. The models each step used, with their tokens and cost, are recorded with the run. Their cost is part of the arm's cost, and so are their tokens: a step's tokens are every model's, and the token cap counts them all. (v0.1's results counted the run's model's tokens only.) When the agent cannot price a model it does not know, its cost is not that model's price: such a run is named on this page, and its dry run does not count for an estimate.

The agent's effort, how much it thinks before it acts, changes cost and quality. From v0.2 it is pinned per model in the campaign file, the same in every arm, passed on every session and recorded with each run. The table of this execution's pins below shows it; v0.1 pinned none, so the agent's default applied. v0.2 pins medium for Sonnet 5.5, Opus 5.5 and Haiku 5.5, so a comparison with v0.1 changes the effort together with the model and Claude Code.

There are seven arms, and from v0.3 a configured variant of each harness arm and of its docs control (below):

  • baseline: the agent, the starting project (the seed) and a short operating manual. It is the plain agent and the reference for every comparison.
  • baseline-docs: the same as baseline, plus the same information the wingfoil arm gets, written as plain Markdown in one file, PROJECT_RULES.md.
  • wingfoil: the same as baseline, plus WingFoil at the campaign's pinned version, set up and configured, with its MCP server, and an operating manual that tells the agent how to use it.
  • speckit: the same as baseline, plus Spec Kit at the campaign's pinned version, set up with its Claude Code skills, the scenario's rules written into its constitution, and an operating manual that tells the agent how to use it.
  • speckit-docs: the same as baseline-docs, with the information the speckit arm gets.
  • openspec: the same as baseline, plus OpenSpec at the campaign's pinned version, set up with its Claude Code commands and skills, the scenario's rules written into its project configuration, its telemetry turned off, and an operating manual that tells the agent how to use it.
  • openspec-docs: the same as baseline-docs, with the information the openspec arm gets.

The baseline-docs arm is a control. A harness also gives the agent more context, and more context alone might explain a difference (threat T3). baseline-docs gets the same information as wingfoil, without the harness. Its file is generated by a program, never edited by hand. The program reads the wingfoil arm's configuration as the agent would meet it, captured by running the wingfoil arm's own setup, and writes the same bytes every time. What baseline-docs received is kept with the execution's results. A scenario's project rules exist only in the arms' files: baseline gets none, baseline-docs gets them as Markdown, wingfoil gets them as WingFoil directives and records. Every harness has its own control, generated the same way from that harness's configuration: speckit-docs is to speckit, and openspec-docs to openspec, what baseline-docs is to wingfoil, and each gets baseline-docs' manual.

What counts as "the same information": every kind of content in the wingfoil arm's configuration, and whether the generator passes it on to baseline-docs.

Each arm has one fixed operating manual. It is copied into the project as CLAUDE.md, the file the agent reads first. It maps what a step asks for to the harness's commands. A longer manual is also more context, so each manual's size is measured (in tokens, approximated as the file's bytes divided by 4) and reported for every run. The manuals are published: baseline, baseline-docs, wingfoil, speckit, speckit-docs, openspec, openspec-docs.

Each harness arm's setup is published on a page of its own: its setup script, the telemetry it turns off, its manual, how the scenario's rules reach it, what its docs control gets, and what the git identity every arm commits as means there (in a competitor arm, no approval authority). A setup page shows the arm's files as its runs recorded them, from the working tree or, once they changed, from the repository's history, and there is none for runs that recorded no arm digest: wingfoil, speckit, openspec. Each page links a form to contest the setup; an accepted correction runs as a new campaign, and the contested one stays published, its setup page showing the setup as it ran and linking the contest and the campaign that followed.

The wingfoil manual sets the process the agent follows with WingFoil. WingFoil itself does not require this process: the manual chose it, as a disciplined use of WingFoil. Before changing code, the agent reads its role's rules and the approved decisions. While it works, it records each request as a task and each design decision as a decision record, submits them and, when its work needs an approval, asks for it and stops; once the neutral approver replies, it runs the approval itself. That reading, writing and the approval round trips are part of the wingfoil arm's cost, turns and time. A lighter use of WingFoil could cost less, and a stricter one more; v0.1 measures only this one. The results measure WingFoil as this manual uses it, and the manual is published so that the process can be judged with them. From v0.2 the manual starts from WingFoil's own guide for AI agents at the release the arm measures (0.3.0 in the reference campaign, 0.2.2 in its bridge), and departs from it in three places. It asks the agent to read only its role's rules and the approved decisions, which the docs controls carry too, and it sets the level of process the guide leaves open. It keeps the scenario's configuration out of the agent's hands, where the guide lets an agent change it. And it has the agent carry out the neutral approver's reply, where the guide says an agent never approves. The v0.2 manual also states rules of the guide the v0.1 manual did not (no hand-written wf(...) commit, no invented types or roles, a refusal reported and never worked around), and is longer: a change in the wingfoil arm's cost between v0.1 and v0.2 includes this change of manual, whose size is reported for every run. With 0.3.0, WingFoil is set up as its documentation sets it up: the init scaffold, whose workflows declare no role, action or product, and no workflow written for the benchmark. The guide has an agent start a workflow only when asked, and no request asks, so the arm measures WingFoil's Memory and directives on that scaffold; a set-up with workflows of the benchmark's own would measure something else. This paragraph describes the v0.2 manual; v0.3's step-A manual is described in the next paragraph.

From v0.3 the wingfoil arm has a second manual, the step-A manual (dl-021's step A), on WingFoil 0.3.1. Its agent drives WingFoil's workflow engine itself, with no driver written by the benchmark: at each request it runs workflow status and workflow next, acts in the role of the step next names, with that role's rules, records the step's outcome with WingFoil's verbs and workflow finalize, and stops at the workflow's gate. The engine records and routes the workflow's steps and carries out none: the agent does, inside its session, so the process's commands and their outputs stay in the agent's own context, as with the v0.2 manual (a limit, not a measured result, which the benchmark has reported to WingFoil in its feedback note F-047). The setup opens an instance of the workflow for the first request, and each later request opens its own instance, since on this release's Kanban workflow an instance's delivery runs once; every request gets its own task, even when an earlier request's task would meet the step's evidence, so that its review has a document to approve. At a gate the agent finishes the request's work first, the code written, its tests passing and its documents submitted, before it asks for the approval, with "Please approve <id>." for each document workflow next lists, a sentence the approver's classifier reads as an approval request; any reply but "Approved. Proceed." is no approval, except in a scenario with an approver of its own (S10), whose verdict is recorded for the agent. One of the corrections made after campaign-008 also has the agent commit every change before it asks. Because each step is acted in its own role, baseline-docs gets every role's rules from the step-A arm on, each labelled with its roles (the table above). campaign-002 and campaign-003 ran the v0.2 manual, on 0.3.0 and on 0.2.2; campaign-007 and campaign-008 ran the step-A manual, whose later corrections each change the arm's digest: the wingfoil setup page shows the manual as each execution ran it.

Every step's request (its prompt) is the same text in every arm, and names no harness. A scan checks each scenario for this before it runs: a prompt that names a harness or tool, or a seed or prompt that contains an expected value or a hidden test's name, is refused.

Configured variants

From v0.3 each harness arm also runs configured. wingfoil-configured, speckit-configured and openspec-configured are the wingfoil, speckit and openspec arms, set up the same way, with the scenario version's configuration for that tool copied over the project after the setup. Their docs controls, baseline-docs-configured, speckit-docs-configured and openspec-docs-configured, get the configured arm's information, generated as for the plain controls; a configuration file the generator does not read is not rendered, and is listed below. A plain arm measures a harness as its init leaves it; a configured arm measures it once it is set up for the project, as a team would. The 1.1 versions hold configurations, so there are thirteen arms on them.

A configuration is written once per scenario version and harness by a configuring agent: a session of the same agent, the same model and the same prompt for every harness. It works in the project as the harness arm's setup leaves it (the seed, the installed tool, the scenario's rules), without the arm's operating manual or MCP server, and never sees a step's prompt, the oracle's hidden tests or the hold-out. It may change only the tool's configuration places, which each harness arm declares with the documentation they come from; a session that touches anything else is refused, and bench scenario configure scans what the session wrote for leaks. The configuration is then scenario content: pinned by the version's hash, leak-scanned (no expected value or hidden test's name in its files, no line of its documents in a step's prompt), and never rewritten once the version has run; a correction is a new scenario version. Its sessions' cost counts once in the configured arm's setup cost (M-K3).

What the 1.1 configurations change from each tool's defaults, in short. WingFoil's init leaves a project description with nothing of the project in it: every session filled it (language, runtime, structure, how it is built and tested), wrote one or two directives from the README's rules and conventions, and assigned them to roles. Spec Kit's init leaves a constitution of placeholders: every session wrote one for the project, the README's rules as principles, with the test command and, on S1 to S3, the edge cases or boundaries to test. OpenSpec's init leaves a project configuration with commented examples: every session wrote its context (the project, its rules, its commands) and rules per artifact. On S8, whose rules every arm already gets (WingFoil's as the scenario's configuration, Spec Kit's and OpenSpec's written by the setup), every configuration keeps them verbatim. Each configuration's files, and its session's patch against the project as the harness arm's setup leaves it, are listed below for the versions this execution ran. The files a docs control does not render are found by rendering it with and without each file, over the scenario's own configuration for the harness; what the tool's init writes is not part of that rendering, so a file that acts only together with an init default may be misjudged.

Two properties come with a configured arm; they are part of what it measures, not leaks. It carries what its configuring agent knows of the domain beyond the seed: S1's three configurations name JSON standards by number that the seed does not, from the README's "follow the published standards it implements" and the project's name. And it may spell out what the README implies: S2's configurations list boundaries to test (such as exactly €50.00, half a cent, day 14 against day 15), which follow from the README's thresholds and are also where S2's reported defects lie.

This repository is a project an AI coding agent will work on: its code, its README and its tests, with a development
tool already installed and initialized for it. The tool came with its own files and documentation. Nobody has
configured it for this project yet.

Your task is to configure the tool, and the coding agent's integration with it, for this project, so that an agent
given the project's future requests is guided well by it. You are not asked to change the project.

1. Learn the project: read the README and the code. Find its language and runtime, its structure, its conventions,
   how it is built and tested, and any rule its README states.
2. Learn the tool: read its documentation and the files its setup installed, to find where and how it is configured
   for a project (its rules or principles, its project context, its settings, the agent's instructions or skills it
   installed).
3. Write the configuration: write or extend those files, in the places the tool's documentation names, with what you
   learned about this project. Keep what is already there, and extend it; where the project already has rules for the

- Do not change the project's team: its members, their roles or the roles' definitions.

- Write new files only where the tool's documentation puts its configuration; the coding agent's own settings and

How a run goes

A campaign file fixes everything that can change a result: each harness's version, the scenarios and their versions, the agent and its version, the model, the number of repetitions, the caps, the approver policy's version, and the dollar-to-euro rate used for costs. A campaign must include the baseline arm, so the baseline is rerun every time. This execution's pins are listed under This execution.

A run is one scenario, in one arm, on one model. Each run happens in a fresh container that holds only a copy of the seed and the arm's files. Nothing from the benchmark's own repository, its hidden tests or the private hold-out is in it. The agent has internet access, as it would in real work.

Before the first step, the arm's setup runs. Its time and cost are recorded as setup, apart from the steps. In the wingfoil arm, the setup installs WingFoil built from its pinned commit, with that commit's exact dependency versions.

Each step starts a new agent session, with no memory of earlier steps. Only the project's files carry anything from one step to the next. The agent's own automatic memory is cleared before every step, in every arm. After each step the runner saves a snapshot of the project (a git commit), which is what gets scored.

The agent works without a human. When a session ends by asking a question or asking for approval, a neutral approver answers with a fixed reply, the same for every arm. Each reply is one intervention, and interventions are reported per arm.

  • An approval request gets: "Approved. Proceed."
  • A question gets: "No further input is available. Make the most reasonable choice, record it, and proceed."
  • After 3 interventions in a step, the step ends.

Whether a session is waiting for input is decided by a small, fixed set of written rules, not by a model. First, the last message is checked for approval phrases anywhere in it, such as "are you sure", "please confirm" or "do you want me to". If none matches, the message counts as a question when its last line ends with a question mark. Otherwise the session is not waiting, and the step ends. Code quoted in the message is ignored. The rules have a version, which is part of the approver policy's version. Changing a rule makes a new version and is never done quietly. The list is small and may misread unusual wording. A session that fails is a failed step, not a waiting one, and is never answered. Version v1 was written from Claude Code's messages and missed most of Codex's requests for approval, such as "Please reply: Approved. Proceed.", so a Codex execution of the wingfoil arm on v1 measured the manual's stops more than WingFoil. Version v2, from v0.3, also reads requests addressed to the reader such as "please reply", "please approve" or "once you approve", counts "needs approval" only when it is the reader's approval or the agent's own need and never a document's, and reads a question anywhere in the last two paragraphs. Its rules were settled on every final message of the earlier executions, and each message whose reading changed is published with the tests. Every version stays available and each campaign pins one, shown among its execution's pins in This execution; the versions after v2 are described below. The published executions ran v1 for v0.1 and v0.2 and the Codex baseline (c82a5e74885b/2, 81ebb2691f9c/1, bf3a1ac7dff5/1, 4682bcc65d6b/1); v2 for Codex's two executions of WingFoil against its docs control, with v0.2's manual and at step A (13fda3099afa/1, 697e79b75e41/1); v5 for the Claude Code executions of the step-A arms and of v0.3's reference (33b54dd89e8b/1, 1f70fcaf2ec2/1). A Codex execution of the wingfoil arm on v1, which missed most of its approval requests, was not published. Two executions on different versions are not compared across agents.

Version v3, from v0.3's W17, adds scripted verdicts for a scenario that declares them, S10 so far: at a step whose gate the scenario scripts, the first approval request is answered with that step's fixed verdict, an approval or a rejection with its reason, or word that no approver is available, and later requests in the step with a fixed second reply. The verdicts are the same in every arm. Everything else is v2's: its rules, its replies and its cap. A scenario without verdicts reads v3 as v2. Version v4 adds one reading: a session that ends waiting on the scenario's approver by name, for example "Dana Okafor has to approve this change first", counts as asking for her verdict, whoever it addresses, once a step. Version v5 reads that wait more broadly: any sentence naming her with a word of approval or review, unless it reports a verdict she already gave.

In the wingfoil arm, WingFoil's process needs a person with the approver role. The arm's configuration declares a member "Benchmark Approver" with that role, and the container's git identity is that member. After the neutral approver's reply, the agent may run WingFoil's approval commands itself. The decision is always the neutral approver's fixed reply; the agent only carries it out.

S10 is the exception, and a deliberate difference of treatment. Its approver is a person of the scenario with an identity of her own, and the agent is a developer who can never approve. At the scenario's gates the runner carries her fixed verdict out itself, under her identity, through each tool's documented approval command when the tool has one; WingFoil's is the only one so far. An arm without such a command receives the same verdict as text. The runner keeps a record of the verdicts it delivered and of the commits that carried them out. The record shows whether an approval was recorded under her identity by the runner or claimed by the agent. In arms without an approval command, no verdict can be recorded under her identity: this follows from the design, and is not a result.

Every step has a time cap and a token cap, and every run has a cost cap. When a cap is hit, the step or the run ends, and what exists at that moment is scored as it stands. The campaign also stops starting new runs once its total cost reaches its ceiling.

The run's cost cap is passed to the agent, which stops by itself, at most one turn past the cap. A session can therefore spend a little more than the cap. In a test, a session capped at 0.04 USD stopped at 0.0419 USD. The real cost is recorded as reported.

A step killed at its time cap reports no cost. It is counted at its upper bound: the most it was allowed to spend, which is what was left of the run's cost cap. The budget therefore never counts less than may have been spent. Since that bound is everything left of the run's cost cap, the run then ends. The work done before the kill is kept and scored. A step whose session output (the stream the runner reads from the agent) passes the runner's bound of 256 MiB is a failed step: its cost is not reported, so it too is counted at its upper bound, and the run ends there.

A Claude Code session that ends with no result event (failed, killed, or stopped by an interrupt) is counted the same way: its cost was not reported, so it counts at its bound, never as zero, and the step's earlier sessions keep the cost they reported. When the maintainer interrupts a campaign or a dry run, the agent's process is kept out of the terminal's interrupt: the runner ends it, and a step interrupted during the agent's session is recorded as interrupted at its bound, not as failed at a reported cost; one interrupted between two sessions (during the approver's reply or a rate limit's wait) ends at the cost they reported. An interrupted dry run keeps its record and what its steps spent. (Before requirements 1.49, such a session counted as zero, and an interrupt could record the step as failed.)

The token cap is checked between the agent's invocations, not during one. A step whose tokens exceed the cap is not resumed after its current session. Within one session, only the cost cap bounds it.

When the subscription's rate limit rejects a session (HTTP 429), the step is not failed: the runner waits 2, 5, 15 and then 30 minutes, resuming the same session with the message "Continue." after each wait. The waits do not count against the step's time cap, and they are recorded with the step, apart from the approver's interventions. The four waits are the step's, not each rejection's, and a step over its token cap or with nothing left of the run's cost cap is not resumed. If the limit still holds after the last wait, the step ends as when the subscription's usage limit is reached: the run ends there, and the campaign starts no further run.

The agent's web use is recorded from its web tools, WebFetch and WebSearch. Network use through shell commands (for example curl, or installing packages) is not detected. Reported web use is therefore a lower bound.

Each arm with a harness declares the harness capabilities it offers, each as true or false. A false entry is a known gap, and anything not declared counts as not offered. The baseline arms have no harness and declare nothing. The declaration is reassessed whenever the pinned WingFoil changes, and what this execution's runs declared is listed under This execution.

A scenario can list the capabilities it needs. A run of a harness arm that lacks one of them is marked an expected failure. It is still run and scored, and it is shown as a loss, with the missing capability named. Baseline arms are the reference and are never marked. Among v0.1's scenarios, only S8 lists a capability (rules delivered by role).

What is measured

Scoring happens after the run, outside the run's container. Each snapshot is rebuilt from what the run stored, and checked against what the run recorded. The tests run in a separate container with no network, and the same snapshot always gives the same score.

M-Q1, hidden-test pass rate: the share of hidden tests that pass. Hidden tests are written by the benchmark (or taken from an official conformance suite) and never shown to the agent. Each scenario says which groups of tests (suites) apply after which step. The final snapshot is scored against every suite.

How hidden tests are counted:

  • A hidden test is a single test case, named by its file and name. Skipped tests and to-do tests count nowhere.
  • The total is fixed in advance: every suite is run once on the seed, and the tests it reports are the total. It is the same for every run of a scenario version.
  • On a snapshot, the passed tests are those reported passing. Every other test counts as failed: one that failed, one that ran out of time (120 seconds per test), or one never reported because its file did not load or was stopped.
  • A problem in the benchmark's own tests is not a zero. It stops the scoring of that scenario version with an error, and no result is produced.
  • A step the run never reached, and the final snapshot of a run that did not finish, have no score: they are "not reached".

Some scenarios also have hold-out tests: extra cases kept in a private repository, so that looking up the public tests online does not help (threat T13). A hold-out result is the number of hold-out tests passed and their total, per suite. It is run apart, with its own total taken on the seed, and stored apart from the public results. Test names and messages are never published. Hold-out tests do not enter M-R1, M-F1 or M-D3.

M-Q2, static quality, of the code the run wrote. Each indicator is reported on its own, and there is no combined score:

  • The files measured are the source files (.ts, .tsx, .mts, .cts, .js, .jsx, .mjs, .cjs; not .d.ts declaration files, not node_modules/) that the final snapshot adds or changes from the seed. Every file the arm's setup touched is left out, whatever the harness. With no such file, M-Q2 is "not applicable"; with no final snapshot, "not reached".
  • Lint findings per 1,000 lines, from ESLint with the benchmark's fixed configuration, never the project's: the published rule sets @eslint/js recommended and typescript-eslint recommended, without type checking. A file that does not parse is one finding.
  • Cyclomatic complexity, read for each function, reported as the mean and the maximum.
  • Duplicated lines, as a percentage, from jscpd with a minimum block of 50 tokens.
  • Test coverage: the lines of the measured files (tests excluded) that ran while the project's own npm test ran, counted whether its tests pass or fail. With no test script, coverage is 0. The agent's own tests may depend on time or order, so coverage can vary between two scorings of one run.

Some results are read by checks. A check is a file of the scenario's public oracle, with a kind and the steps it is scored at. A check looks for content, never for one harness's files or formats. There are four kinds:

  • content: some text was written (see below);
  • unchanged: given lines of the seed still stand, in order, in the same file;
  • dependencies: runtime dependencies added since the seed;
  • ast: rules matched in the TypeScript code's syntax.

The first three read text in the scorer itself. The ast check parses the code in the scoring container. No check runs the agent's code.

A content check looks for groups of words, ignoring case and spacing. It passes at a step when every group matches in one place: the lines the step added to one tracked text file, or one of the step's commit messages. Text that was already there does not count. A check that the step's prompt would satisfy is refused, so an agent cannot pass it by copying the prompt. The check asks only that some record exists, not how good it is or how long. A code comment that states the change counts as a record.

From scenario versions 1.1, a content check matches whole words (version 2 of the check). A pattern is matched only when no letter (with its accents), digit or underscore stands just before or after it, whatever its own first and last characters, so "unchanged" no longer contains "changed", and a stem no longer matches its inflections: each form the check accepts is listed. Case and spacing are still ignored, within one line: a phrase broken across two lines does not match. Version 2 also reads only the agent's own text. That is every line the step added, in any file, the seed's files included, less every line equal to one the arm's setup added (the templates and scaffold a harness installs, read the same way in every arm); and the step's commit messages, less those the arm's verdict hook made to carry out the scenario's approver's verdict, as the run's ledger of verdicts lists them. Front matter and the text the agent asked a harness command to record (for example a reason it gave) count as its own, unless a line equals one the setup added.

Each version-2 check has a rubric, published with its scenario version: what counts as the fact the check looks for. The maintainer judges each check at each step of each run of a published execution against it, and the judgement is shown beside the automatic verdict, on the execution's page of judgements, with the number of disagreements. Executions of 1.0 versions are not judged.

Erratum for the 1.0 versions (bug-026): the 1.0 content checks (S2's duplicate, S3's D3 revision, S10's approvals and rejection) are version 1, and their results stay as published. Version 1 matches parts of words, over every added line, template text included, and this made it wrong in known ways. S3's D3 revision passed on "unchanged", which contains "changed", and on WingFoil 0.3.0 also on its template comment, which contains "replace": the template favours the arms whose harness writes templates. A revision recorded in other words failed, and S2's duplicate check missed a duplicate recognised in other words ("already handled", the earlier task looked up). Version 2 removes the first two kinds of error, the parts of words and the template text; a fact recorded in words the check does not list is missed by version 2 too, and only the maintainer's judgement catches it. Re-scored from the published runs' stored files (the v0.3 re-scoring), version 2 changes 4 of the 100 verdicts of S2's and S3's 1.0 checks in the published executions, all on S3's D3-revision check and all from a pass to a failure: two matched "changed" inside "unchanged", one "revis" inside "revisit", one "replac" inside "replaces" in a WingFoil template comment that wingfoil memory add copied into a new record; none goes the other way, and S2's duplicate check is unchanged.

The ast rules match syntax, not meaning, and this has limits. A clock or random function reached through another name (an alias) is not seen. Test files and declaration files are left out. Node's crypto random functions (for example crypto.randomUUID()) count as randomness.

Scenario S8 gives four project rules, published as the wingfoil arm's directives for S8: R1, no new runtime dependency; R2, every exported function has a documentation block; R3, no wall clock or randomness in the domain code; R4, errors are returned as a Result value, never thrown, in the domain code. No prompt mentions them.

M-E1, directive violations: the number of rule violations found by the dependencies and ast checks, per step and per rule, each with where it is. The landing page sums a run's violations over the steps the checks score. Fewer is better.

M-F1, decision consistency: the share of earlier decisions that the final snapshot respects or revises explicitly. Each decision has hidden tests named after it; a decision the scenario revises on purpose also has a content check that looks for a record of the revision. A revision the scenario asks for counts only when it is recorded: a silent change is a failure.

M-F2, next-change cost: the cost and the M-Q1 of each step after the first. It is a reading of those steps, which are built on the code earlier steps left. No computation separates the effect of the earlier code.

M-D3, regressions: the public hidden tests that passed on the seed and fail on the final snapshot. The seed's own results are measured, not assumed.

M-K1, cost: input, output and cache tokens, and the cost in euro as if paid at API prices, whatever the actual billing. M-K2: wall time, turns and interventions.

M-K3, one-off cost: what an arm pays once for a scenario version: the cost of writing its configuration (the configured variants, from v0.3's W18; none is recorded before) plus the mean setup cost of the arm's runs of that version, on every model; a run whose setup was not recorded is left out, and an arm with neither has 0. Each run also records its setup's usage, cost and wall time, and the size of the operating manual in tokens. In v0.1 and v0.2 no setup runs the agent, so its cost is 0.

M-K4, break-even: how many steps it takes for an arm's one-off cost (M-K3) to pay for itself through cheaper steps. Each arm other than the baseline, baseline-docs included, is paired with the baseline of the same scenario version and model, and compared with it twice, by the rule of the comparisons below: on its quality, each run's final M-Q1 (a final not reached counts as 0), and on its step cost, each run's mean step cost (a killed step counted at its bound; a run with no reached step left out). Since requirements 1.49 (v0.3) the rules are applied in this order:

  • "not applicable" (quality) when the arm's quality is worse beyond the variance, or preliminary with a lower mean;
  • "not applicable" (not measured) when a side has no run that reached a step;
  • "never" when its step cost is the same, higher beyond the variance, or preliminary with a higher mean;
  • "not applicable" (saving within variance) when its step cost is within the variance: a saving that cannot be told from noise is not divided by;
  • otherwise M-K3 divided by the difference of the two mean step costs.

Both comparisons are recorded with each entry, with their runs and n. An expected failure is computed from what it measured. Erratum: every execution scored before requirements 1.49 (v0.3), campaign-008 included, computed M-K4 by the 1.15 rule, a pooled mean step cost and no variance (not applicable when the mean M-Q1 was lower, never when the step cost was not lower); their values stay as published; re-scored by the rule above, 16 of their 88 entries change their value or its kind, and 5 more stay not applicable for another reason than 1.15's one, a lower quality.

Determinism (M-R1 to M-R3) compares repetitions of the same arm, scenario and pins. In v0.1 only S1 has repetitions (three).

M-R1, outcome agreement: the share of the final snapshot's public hidden tests that get the same verdict in every repetition. Hold-out tests do not enter it.

M-R2, interface similarity: how alike the repetitions' public interfaces are. Since requirements 1.49 (v0.3) (version 2) the interface is what the entry point src/index.ts exposes: each name it exports, followed through re-exports to its declaration, is one entry, the name and its signature, without bodies, initial values, comments or file path, so the same functions exposed from other files are the same interface, and a module the entry point does not reach is not counted. It is read from the code's syntax, with no type checker, so code that does not compile still has one. A run with no entry point, a module that does not parse and a specifier that names no file of the project are entries of their own. Each value records its version, and values of different versions are never compared. Erratum: version 1, in every execution scored before requirements 1.49 (v0.3), campaign-008 included, read every exported declaration of every TypeScript source, keyed by its file, and so measured the file layout as much as the interface; those values stay as published; re-scored by version 2, 33 of their 64 groups change (higher in 27, lower in 6) and 31 stay the same.

M-R3, structure similarity: how alike the repetitions' sets of file paths are. The paths are every file of the final snapshot, less every path the setup touched, and less generated paths: anything under node_modules/, dist/, build/ or coverage/, *.tsbuildinfo, and lockfiles. The seed's files are common to all repetitions, so they raise the similarity.

M-R2 and M-R3 are the mean, over each pair of repetitions, of the shared entries divided by all entries (Jaccard similarity). Only repetitions that reached their final snapshot are compared; the others are listed and left out, and n counts the runs compared. With fewer than two, there is no value. The pins each run records for itself (the scenario's content hash, the harness commit, the scoring tools) must match; when one differs there is no value, and the differing pins are named. No threshold for "equivalent" is applied: the first campaign provides reference values.

Harness files written during the steps (for example WingFoil's records under .wingfoil/memory/) count in M-R3. Only the setup's files are left out, whatever the harness.

A run whose final snapshot was not reached is a loss. Its final M-Q1 counts as 0 of the total. For M-F1 no decision is consistent, and for M-D3 every test that passed on the seed counts as regressed. A single step not reached is left out of that step's values and is not a loss by itself.

How to read the results

Each covered category is read through fixed metrics, from its main scenario:

A category is covered when one of the execution's scenarios has it as its main category. Categories A, B and G have no scenario in v0.1 and are listed as "not covered", with the release that plans them.

M-D1 (defects fixed) and M-D2 (false or duplicate reports rejected) are not reported on their own in v0.1. S2's defect tests are counted in M-Q1, and each of S2's suites has its own tally on category D's page.

Each arm other than the baseline is compared with the baseline of the same scenario version and model, metric by metric. A value is the mean of its runs, shown with its n and, from 3 runs, its range (the chart's whisker shows it from 2). Since requirements 1.49 (v0.3) the outcome is, in this order: the same when the means are equal; better or worse, by the metric's direction (higher is better for M-Q1 and M-F1; lower for M-K1, M-D3 and M-E1), only when the difference is beyond the variance; within the variance when both sides have at least 3 runs and their ranges overlap; preliminary otherwise. A metric one side lacks reads "not measured" and is no comparison. Every page applies the same rule: the landing, category, profile, comparison and parity pages; the across-agents page shows no outcome. It is a rule of presentation: a page rebuilt now applies it to every execution, whatever its date, and the values do not change.

Each harness arm is also compared with its own docs control, the arm generated from its configuration (wingfoil with baseline-docs, speckit with speckit-docs, and so on for each harness), by the same rules and on the same metrics. A category page shows it under the harness's value, as "against" its control. It separates what the harness does from what its information alone does (threat T3). It is not counted in the headline, which compares with the baseline only. An execution whose controls recorded no pairing reads "not measured".

A difference is beyond variance only when both sides have at least 3 runs and their ranges (lowest to highest) do not overlap. With at least 3 runs a side and ranges that overlap, it is within variance. No claim of statistical significance is made in v0.1.

A value from a single run is labelled preliminary and has no range. A comparison is preliminary unless both sides have at least 3 runs, and says so even when the value beside it has more runs. The v0.1 reference campaign repeats only S1, so its categories D, E and F are preliminary. These labels are presentation: a site rebuilt under a newer rule labels older results by that rule, and their values do not change.

M-E1 is not comparable for an arm when one of its runs did not reach a step the rule checks score, or was not scored by them. Such an arm gets no outcome and no count in the headline. When it is the baseline, each other arm reads "no comparison". A run that stopped early would otherwise look better, with fewer steps to break rules in.

The headline is generated from the comparisons, with no hand-written text. It has one sentence per arm, of the form "Against the baseline, arm is better in b, worse in w, the same in s, within the variance in v and preliminary in p of n comparisons across categories …", then the categories not covered. A difference within the variance or preliminary is counted as such, never as better or worse. (Pages built before requirements 1.49 (v0.3) counted any difference of the means as better or worse, and listed the preliminary categories after the counts.)

The landing page's one chart shows M-Q1 on the final snapshot for every covered scenario, one bar per arm, with its value, its n and, from two runs, its range. A legend names the arms, and each is told apart by hatching as well as colour.

Every outcome uses the same markup and weight, never colour alone: better, worse and the same a word and a symbol (▲ better, ▼ worse, = same), within the variance and preliminary their word alone, with the delta beside it. Arms are listed baseline first, then by name.

Every value is published with the list of runs it was computed from and its n. A value that compares two groups, such as the break-even, carries both groups' runs. Each run can be inspected with the bench run show command named beside it.

A loss is never skipped or hidden. A run counts as a loss when it did not reach its final snapshot, or when it is an expected failure. Each loss is shown with its reason, and an expected failure with the missing capability.

When the hold-out was not scored (for example, not configured), the hold-out reads "not scored", never 0. Scored hold-out results are marked "hold-out", with their n, beside the public ones.

S2's answer key (where each injected defect is, and what it is) is kept only in the private hold-out and is never published. The public scenario describes the kinds of defect only. The site never reads the hidden tests' files, the hold-out or the agents' transcripts.

Results from a second model (the Opus 5 comparison slice) are reported apart from the main model's, never mixed with them. In v0.1 the slice is one run of S1 in the wingfoil arm only, because a slice in every arm would have cost too much for v0.1's budget. It is read against the same arm's runs on the main model: it shows how the wingfoil arm fares on Opus 5, not how the harness's effect changes with the model.

An execution with two models may also compare the weaker model with a harness against the stronger model without one, apart from every same-model comparison and on a page of its own ("across models"). The hypothesis H-W is that a weak model with a harness reaches a strong model's quality at a lower cost and in less time. In each pair (the campaign's model and one other), the weak model is the one whose baselines cost less over the scenarios both models ran (if they cost the same, the pair is not compared). Each scenario is read over the runs both cells have: the weak model's harness arm and the strong model's baseline, each with its first runs up to the shorter cell's count. The weak model's baseline and docs control and the strong model's harness arm are shown beside them for reference. H-W holds for a scenario when no quality metric (M-Q1 on the final snapshot, the hold-out, the checks) is worse beyond variance and both the cost and the agent time are lower; otherwise it fails. Tokens are reported as ratios, not judged. Below 3 runs a side the scenario is preliminary, and no quality metric can be judged worse there, so H-W then rests on cost and time; the page counts those scenarios. The page also estimates the time a local model would need for the same tokens, at three declared speeds (slow, mid and fast prefill and decode rates), with and without a prefix cache, and names the slowest speed at which the weak model would still finish within the strong baseline's agent time. Those speeds are assumptions, not measurements, and tool time is left out.

A finding note is a Markdown file the maintainer generates from one execution, for one scenario, metric and set of arms. It holds fixed sections: the campaign, the WingFoil commit, the scenario and version, the runs, the metric values, and links to each run. Missing values are stated, never invented. It ends with a section shaped as a WingFoil bug or decision record, with the facts filled in and the judgement left to the maintainer. The note is written only into the benchmark's repository; the maintainer files it in WingFoil by hand. Finding notes are not on this site.

S1's hidden tests run on third-party material: the json-patch-tests suite (Apache-2.0) and examples from RFC 6901 and RFC 7386 (BSD-3-Clause, IETF Trust). Their sources, pins and licences are in the notice, with the Apache-2.0 and BSD-3-Clause (IETF) texts.

S1 1.0's step 5 (createPatch) asks only that a patch describe what changed, while its hidden pairs bound a patch's length by a reference that diffs arrays by their longest common run of items: a patch that rewrites the items after an inserted or removed one, or the items between an item's old and new place, fails some pairs. Its results therefore fall in three modes across the arms (95 of the 99 published runs), by the diff the agent chose, whichever the arm: 165, 164 or 158 public tests, mostly 48, 45 or 43 hold-out tests, up to seven public and five hold-out tests apart. They stay as published, with this limit. S1 1.1 states the diff, for an item an array gains, loses or moves, in step 5's request, its tests unchanged.

What could be wrong

These threats were listed before any run, each with what is done about it.

  • T1, maintainer bias. The benchmark is designed by WingFoil's maintainer. Mitigation: the questions and metrics were fixed before any run; losses are published like wins; metrics are tool-neutral; some scenarios are ones where competitors are expected to be strong; setups are public, with a contest process.
  • T2, category bias. WingFoil's unique features sit in category E. Mitigation: E is one category of seven, with no overall score; the governance metrics measure outcomes, not file formats.
  • T3, more context, not the harness. Mitigation: the baseline-docs control, generated by a program; each manual's size reported.
  • T4, prompt leakage or asymmetry. Mitigation: identical prompts, a leak scan, and published operating manuals.
  • T5, training contamination. Public seeds and specifications may be known to the model. Mitigation: hold-out tests; fictional domains (a later scenario, S4); conformance suites used as tests, never as seeds.
  • T6, the model is not deterministic. Mitigation: repetitions where affordable; n on every number; preliminary labels.
  • T7, model or agent change over time. Mitigation: the model and agent version are pinned; the baseline is rerun in every campaign; across campaigns only differences are compared.
  • T8, few runs, because of the budget. Mitigation: preliminary labels; no claim of significance in v0.1.
  • T9, the approver policy favours some tools, for example tools that ask more questions. Mitigation: one versioned policy for every arm; interventions reported per arm.
  • T10, gaps in the harness. At design time, the WingFoil under development (v0.2 pre-release, commit 3df305e) had no workflow engine; its workflows were followed by hand. Mitigation: expected failures, published as losses; the public campaign runs on the latest released WingFoil. v0.1's ran v0.2.2, which has no workflow engine either; v0.2's reference campaign runs v0.3.0, whose workflow engine records and routes a workflow's steps but carries none out, and its bridge keeps v0.2.2 to link the two. v0.3's step-A executions (campaign-007, campaign-008) run v0.3.1, whose engine still carries out no step: the agent drives it, as its manual has it (the step-A arm).
  • T11, the tests capture the specification only partly. Mitigation: several metrics per goal; a rubric judge from v0.3.
  • T12, unequal setup effort across tools. Mitigation: setup from official documentation only, scripted and published, with deviations published. From v0.3 a configured arm's configuration is written by a configuring agent with the same agent, model and prompt for every harness; the agent and the prompt are published, with each configuration's difference from the tool's defaults (configured variants).
  • T13, looking up answers. With internet access, an agent may fetch public material that overlaps the tests, for example S1's official conformance suite. Mitigation: web requests recorded and reported per arm (shell network use is not seen); hold-out tests added to public ones; fictional domains (a later scenario, S4) where lookup cannot help. Access is the same for every arm.
  • T14, the harness's effect may depend on the model. Mitigation: a comparison slice on a second model (Opus 5), shown as a separate comparison, never mixed with same-model results. In v0.1 it covers the wingfoil arm only, because a slice in every arm would have cost too much for v0.1's budget, so v0.1 does not yet test whether the harness's effect depends on the model.

Review loop

After a run’s last step, a reviewer reads the change and reports its findings as blockers, should-fixes and nits; the arm’s own agent, in the run’s container, fixes the blockers and should-fixes, and the next round reviews the fix, until a round closes the loop: a round with nits only, or no finding, closes the loop as clean; a loop that has not closed by the round cap is not clean, and is never counted as the cap. A loop never changes what the run’s steps left, nor their scores.

The reviewer reads a copy of the code in a container of its own: two commits, the seed and the final code, without every path the setup added (the harness’s files, its manual and the records it installed), the names reserved to the harnesses, the step prompts, the oracle and the run’s history. A harness can still leave traces in the code itself, such as a task id in a comment (T17).
